# 监控体系对比

> 验证环境:纯文档,无依赖;以 Prometheus + OpenTelemetry 为统一基线(2026-08 主流)。

**一句话:** Java 有最成熟的监控生态(JMX + Actuator + Micrometer),但**其它语言的对应物完全找得到**——Go 的 pprof/expvar、Python 的 prometheus_client、Node 的 prom-client、PHP 的 FPM 状态页;链路追踪统一走 OpenTelemetry。

## 监控能力对照表

| 维度 | Java | Go | Python | Node.js | PHP |
|---|---|---|---|---|---|
| 指标库 | Micrometer(Actuator 自动暴露) | prometheus/client_golang / expvar | prometheus_client | prom-client | 第三方包 / FPM 状态页 |
| 默认端点 | /actuator/metrics(JSON) | /metrics(手动注册) | /metrics(手动注册) | /metrics(手动注册) | /status(fpm_status) |

## 关键差异

### 1. Java 的「默认监控」在别处要自己搭
- Spring Boot Actuator 开箱即暴露 health/metrics;Go/Python/Node 都要手动注册 `/metrics` 并暴露进程指标。
- 心智转换:监控不是框架送的,是你要写 5–10 行代码接的。参考:各语言 `09-监控.md` 模块给最小接入示例。

### 2. Go 的 pprof 是「内置最强剖析器」
- `net/http/pprof` 一个 import,就能拿到 CPU、堆、协程、锁的火焰图——对标 JFR,但接入成本低一个数量级。
- Java 开发者必学:排查 Go 内存/性能问题,`go tool pprof` + 火焰图是标配。

### 3. 运行时指标的可观测性差异
- JVM:GC/线程/堆全部开箱可见,调优文化建立在这之上。
- Go:runtime/metrics 有 GC/goroutine/内存统计,但指标粒度粗,「调优」空间小(官方刻意为之)。
- Python/PHP:进程级指标有限,内存问题更多靠外部(容器 cgroup、日志)。

### 4. 链路追踪:全语言统一
- 无论哪门语言,方案都是 **OpenTelemetry SDK + Collector + 后端(Jaeger/Tempo/SkyWalking)**。
- Java(SkyWalking agent)习惯的「无侵入接入」在 Go/Node 不存在——需要手动埋点(或借助框架中间件)。

## 统一监控栈建议(跨语言团队)

```
应用(各语言 SDK)
  ├── /metrics → Prometheus → Grafana
  ├── 日志(stdout) → Loki/ELK
  └── OTel SDK → OTel Collector → Jaeger/Tempo/SkyWalking
```

- 指标:统一 Prometheus 格式(各语言库都兼容)。
- 日志:统一 stdout + 结构化(JSON),采集层不关心语言。
- 追踪:统一 OpenTelemetry 语义约定,跨语言调用链才能串起来。
- 告警:统一 Prometheus Alertmanager 规则(按服务,不按语言)。

## 常见误区

- ❌ 以为 Go/Python/Node 没有监控生态:Prometheus 客户端是标配,只是要自己接。
- ❌ Java 的 JFR/Arthas 式「进程内深挖」思维:Go 用 pprof 对位,Python 用 py-spy。
- ❌ 每门语言搭一套不同监控后端:Prometheus + OTel 全语言通用,别造轮子。
- ❌ 只接指标不接链路:微服务跨语言场景,没有 trace 定位问题靠猜。
- ❌ 日志写文件再采集:统一 stdout,交给采集器,别自己管文件轮转。
