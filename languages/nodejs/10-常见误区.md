# Node.js · 10 常见误区(Java 思维移植的坑)

> 锚点:把 Java 的习惯直接搬进 Node.js 会踩的坑。
>
> 验证环境:纯文档,坑位来自前 09 个模块的实测与 Node 社区共识。

| # | 误区(Java 思维) | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 以为多线程并发 | 单线程事件循环,无数据竞争也无并行 | 并发 = 异步编排(Promise.all),CPU 密集用 worker_threads |
| 2 | 同步文件 IO(readFileSync)处理请求 | **阻塞事件循环,拖垮所有连接** | fs.promises 异步版 + await |
| 3 | 忘 await 异步调用 | 假绿测试 / 竞态 / undefined | 每个异步操作都 await;测试里尤其注意 |
| 4 | 用 `==` 比较 | 类型转换陷阱(`1 == "1"`) | 一律 `===` |
| 5 | 用 var 声明 | 函数作用域 + 提升,诡异行为 | let / const |
| 6 | 用 Object 当 HashMap | 键限字符串 + 原型污染风险 | Map(任意键、保序) |
| 7 | 找 synchronized/锁 | 单线程无竞争,无需锁 | 异步时序问题用 Promise 编排 |
| 8 | 单实例部署 | 只用到一个 CPU 核 | pm2 -i max / cluster / K8s 多副本 |
| 9 | 生产用 npm install | 依赖浮动,不可复现 | npm ci(lock 精确) |
| 10 | 不配校验(裸手写) | 参数错误直接炸/安全漏洞 | Fastify schema / zod |
| 11 | Express 4 async handler 抛错不处理 | 未捕获拒绝,进程崩溃 | 用 Fastify/NestJS,或 try/catch 包装 |
| 12 | 忘 try/catch 异步 | unhandled rejection 进程退出 | async 函数内 try/catch 或 .catch() |
| 13 | 回调里做重计算 | 阻塞事件循环 | worker_threads / 拆分异步 |
| 14 | 用 setTimeout 当 sleep 阻塞 | 不理解异步语义 | await delay() 封装(Promise) |
| 15 | 不监听事件循环延迟 | 阻塞早已发生却无从发现 | prom-client eventLoopLag 指标 |
| 16 | 内存泄漏无感知 | 长驻进程内存持续上涨 | --heapsnapshot + DevTools(≈ MAT) |
| 17 | 多实例后依赖进程内状态 | 实例间状态不一致 | session/缓存/锁外部化(Redis) |
| 18 | 忘处理流错误(stream 'error') | 未捕获异常崩溃 | stream.on('error') / pipeline() 包装 |
| 19 | 大 JSON 一次性 parse | 内存翻倍 + 阻塞 | 流式解析(JSONStream)或分批 |
| 20 | 忽略 TS | 大项目维护成本失控 | 新项目默认 TypeScript |

## 总结

Node 的哲学是「**异步优先 + 单线程**」。Java 开发者移植的关键转变:并发思维从「多线程 + 锁」换成「事件循环 + 异步编排」;部署思维从「单进程多线程」换成「多实例」;排查手段从「线程 dump」换成「事件循环延迟 + 火焰图」。这三换完成,Node 的生产力优势(IO 密集场景)就完全拿到了。
