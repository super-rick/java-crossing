# Node.js · 04 并发编程(Event Loop 心智模型)

> 锚点:Java 的「线程 + 锁 + 线程池」对应 Node 的「单线程事件循环 + 异步编排 + worker_threads(特殊场景)」。
>
> 验证环境:Node 22.23.0(实测输出)。

**一句话:Node 没有多线程并发——一个进程一个 JS 线程,高并发靠「异步不阻塞」;Java 的锁/线程池/并发容器在 Node 里基本用不上,问题变成了「别阻塞事件循环 + 正确编排异步」。**

## 并发原语对照表

| 概念 | Java | Node.js |
|---|---|---|
| 并发单元 | Thread(OS 线程) | **回调/事件/微任务(单线程内交错)** |
| 并行单元 | (多核线程) | **worker_threads**(Worker 线程,Node 12+) |
| 异步编排 | CompletableFuture | **Promise / async-await** |
| 多路等待 | allOf / anyOf | **Promise.all / Promise.race** |
| 锁 | synchronized / Lock | **不需要**(单线程无竞争) |
| 并发容器 | ConcurrentHashMap | **不需要**(单线程) |
| 线程池 | ThreadPoolExecutor | libuv 线程池(IO 后台,默认 4) |
| 定时任务 | ScheduledExecutorService | setTimeout / setInterval |
| 线程局部 | ThreadLocal | 无(单线程,天然隔离) |

## 完整对照示例(实测)

```js
// 并发 = 异步交错:IO 等待时不阻塞主线程
const delay = (ms, name) => new Promise((resolve) => setTimeout(() => resolve(name), ms));

async function main() {
  const t0 = Date.now();
  // 并行异步(≈ CompletableFuture.allOf)——总耗时 ~300ms 而非 600ms
  const results = await Promise.all([delay(100, "a"), delay(200, "b"), delay(300, "c")]);
  console.log("parallel ms:", Date.now() - t0, results);

  // 顺序 await(串行,≈ 同步调用)——总耗时 ~600ms
  const t1 = Date.now();
  await delay(100, "a");
  await delay(200, "b");
  await delay(300, "c");
  console.log("serial ms:", Date.now() - t1);
}

main();
```

运行:`node main.js`
实测输出:

```
parallel ms: 312 [ 'a', 'b', 'c' ]
serial ms: 613
```

**这是 Node 并发核心**:三个 100/200/300ms 的异步任务,**并行 312ms,串行 613ms**——「并发」在 Node 里就是「同时发起异步、一起等待」。

## Event Loop 工作流程(必懂)

```
┌───────────────────────────┐
│         timers            │ ← setTimeout/setInterval 回调
├───────────────────────────┤
│   pending callbacks       │
├───────────────────────────┤
│       poll               │ ← IO 事件(网络/文件)核心阶段
├───────────────────────────┤
│       check              │ ← setImmediate
├───────────────────────────┤
│   close callbacks        │
└───────────────────────────┘
       ↑ 每轮之间:微任务队列(Promise.then / queueMicrotask)优先执行
```

- **微任务**(Promise.then、await 之后)优先级最高,每阶段结束立即执行。
- 文件/网络 IO 完成后,回调进入 poll 阶段。
- Java 对比:JVM 的线程调度是内核决定;Node 的事件循环是**单线程内的确定性调度**。

## 关键差异

### 1. 阻塞事件循环 = 服务瘫痪

```js
// ❌ 灾难:同步 CPU 密集计算卡死所有请求
app.get("/calc", (req, res) => {
  heavySyncComputation();  // 事件循环停摆,所有连接排队
  res.send("done");
});

// ✅ CPU 密集任务必须交给 worker_threads
const { Worker } = require("worker_threads");
```

- Java:CPU 密集只是占用一个线程,其他线程照常。
- Node:**任何同步阻塞(CPU 密集/同步文件 IO/同步加密)都会冻结整个进程**。

### 2. 异步并发 vs 线程并发的取舍

| 维度 | Java 线程 | Node 异步 |
|---|---|---|
| IO 密集并发 | 线程池(内存大) | 异步(内存极小,万级连接轻松) |
| CPU 密集并行 | 真并行 | worker_threads(有 IPC 成本) |
| 共享状态 | 锁/并发容器 | 无竞争(单线程),但异步时序要小心 |
| 适用 | 复杂计算 + 业务系统 | IO 密集 + 实时交互 |

### 3. worker_threads(≈ Thread 的对应物)

```js
const { Worker } = require("worker_threads");

const worker = new Worker(`
  const { parentPort } = require("worker_threads");
  parentPort.postMessage(heavyComputation());
`, { eval: true });

worker.on("message", (result) => console.log("worker result:", result));
```

- 场景:CPU 密集(图像处理/编解码/大数据计算)。
- 注意:worker 间不共享内存(有 SharedArrayBuffer 可共享 TypedArray),数据通过消息传递(结构化克隆)。

### 4. Promise.all 的「线程池替代」

```js
// ≈ 线程池 + Future.get 的并发收集
const results = await Promise.all(
  urls.map(async (u) => (await fetch(u)).json())
);
```

> ⚠️ Java 思维陷阱 1:找锁/并发容器——单线程下不存在数据竞争,Java 的 ConcurrentHashMap/Atomic 在 Node 里没有对应需求。
>
> ⚠️ Java 思维陷阱 2:以为 async 函数是并行——async/await 只是「异步交错」,不是多核并行;CPU 密集照样卡,必须 worker_threads。
>
> ⚠️ Java 思维陷阱 3:忘 await——`Promise.all(arr)` 不 await 就返回 Promise;await 只写一半(在 for 循环里顺序 await 了本可并行的任务)是常见性能坑。

## 生产模式对照

| 场景 | Java | Node.js |
|---|---|---|
| 并发请求聚合 | CompletableFuture.allOf | Promise.all |
| 首个完成 | anyOf | Promise.race / Promise.any |
| 超时控制 | Future.get(timeout) | Promise.race([task, timeoutPromise]) |
| 限流 | RateLimiter | p-limit 库 / 信号量实现 |
| 重试 | 手写/库 | retry 库 / 手写循环 |
| 取消 | Future.cancel | AbortController |
