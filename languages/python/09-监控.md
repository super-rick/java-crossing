# Python · 09 监控

> 锚点:Java 的 Actuator + Micrometer + JFR/jstack 对应 Python 的 prometheus_client + logging + py-spy/cProfile。
>
> 验证环境:纯文档;版本基线 prometheus_client 0.2x。

**一句话:Python 监控与 Go 同理——「自己接」:prometheus_client 暴露 /metrics、logging 输出结构化日志、py-spy 对运行中进程采样(≈ Arthas 的轻量替代)。**

## 监控对照表

| 维度 | Java | Python |
|---|---|---|
| 指标暴露 | Actuator(自动) | prometheus_client(手动注册) |
| 运行时指标 | JVM 内存/GC/线程 | 进程级(psutil)+ GC 模块计数 |
| 健康检查 | /actuator/health | 自建 /healthz(FastAPI 有扩展) |
| 日志 | SLF4J + Logback | **logging(标准库)** / loguru |
| 性能剖析 | JFR / jstack / MAT | **py-spy**(线上)/ cProfile(离线) |
| 内存追踪 | MAT / jmap | tracemalloc / objgraph |
| 链路追踪 | OTel / SkyWalking | OpenTelemetry Python SDK |

## 指标接入(最小 Prometheus)

```python
from prometheus_client import Counter, generate_latest, CONTENT_TYPE_LATEST
from fastapi import FastAPI, Response

ORDERS = Counter("orders_total", "创建的订单总数")

app = FastAPI()

@app.get("/metrics")
def metrics():
    return Response(generate_latest(), media_type=CONTENT_TYPE_LATEST)

@app.post("/orders")
def create_order():
    ORDERS.inc()   # ≈ Micrometer Counter 自增
    return {"ok": True}
```

- Grafana + Prometheus 采集规则与 Java 服务完全一致(**跨语言统一监控栈**)。

## 日志规范

```python
import logging

# 结构化 JSON 日志(≈ Logback 的 JSON encoder)
logging.basicConfig(level=logging.INFO, format='{"time":"%(asctime)s","level":"%(levelname)s","msg":"%(message)s"}')
logging.info("order created id=%s", 1001)
```

- 生产建议:统一 stdout + 采集器(Loki/ELK),别写文件轮转——与 Java 服务管线一致。
- 结构化字段比 f-string 拼接更利于检索(与 SLF4J 占位符同理)。

## 线上排障:py-spy(≈ Arthas 的轻量版)

```bash
# 对运行中的进程采样调用栈(无需重启、无需改代码)
py-spy dump --pid <PID>          # ≈ jstack
py-spy top --pid <PID>           # 实时热点函数
# 离线剖析:
python -m cProfile -s cumtime app.py   # ≈ JFR 的文本版
```

> ⚠️ Java 思维陷阱 1:等框架送监控——Python 无 Actuator,/metrics 与 /healthz 自己写(FastAPI 下各 5 行)。
>
> ⚠️ Java 思维陷阱 2:线上问题靠重启——py-spy 可以对**运行中** Python 进程采样(不需要 gdb/系统权限特殊配置),先看栈再决策。
>
> ⚠️ Java 思维陷阱 3:GIL 下看 CPU——多线程 Python 进程 CPU 高要区分「真计算」与「锁竞争/切换」,py-spy 栈能直接看到卡在 acquire 的线程。
