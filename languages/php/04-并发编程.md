# PHP · 04 并发编程(进程模型)

> 锚点:Java 的「线程 + 锁 + 线程池」对应 PHP 的「FPM 多进程隔离」;进阶: Swoole 协程。
>
> 验证环境:PHP 8.4.24(实测输出)。

**一句话:传统 PHP 没有线程、没有共享内存、没有锁——并发由「FPM 进程池 + nginx」承担,进程间天然隔离;要 Java 式的高并发编程,用 Swoole/Hyperf 协程常驻模式。**

## 并发模型对照表

| 概念 | Java | PHP(传统 FPM) | PHP(Swoole/Hyperf) |
|---|---|---|---|
| 并发单元 | 线程 | **进程**(FPM 池) | 协程(单线程内) |
| 共享内存 | 堆(线程共享) | **无**(进程隔离) | 进程内共享 |
| 锁 | synchronized/Lock | **不需要**(无共享) | 协程锁/原子操作 |
| 线程池 | ThreadPoolExecutor | **pm.max_children**(进程数) | (协程无池概念) |
| 连接复用 | 连接池 | 请求结束即释放(FPM 持久连接例外) | 常驻复用 |
| 内存缓存 | 应用级 | 每请求重建 | 常驻可复用 |
| 高并发手段 | 线程 + 异步 | **加进程 + 加机器** | 协程 + 常驻 |

## 核心概念:FPM 进程池

```
nginx ──>  FPM master ──>  worker 进程池(pm.max_children)
             每个请求 → 分到一个 worker 进程 → 处理完归还/销毁
```

- **pm.max_children**:最大 worker 进程数(≈ Java 线程池 max 的对应物)。
- 内存占用 = 单进程内存 × 进程数(每个 worker 是独立进程)。
- 调优公式:`pm.max_children ≈ 服务器内存 ÷ 单进程峰值内存`(保守估算)。

> ⚠️ Java 思维陷阱 1:按 JVM 线程池思维调 PHP——Java 线程共享堆,线程数可以大;PHP 每进程独立内存,进程数是「内存预算」决定的,不是并发需求。
>
> ⚠️ Java 思维陷阱 2:找 synchronized/ConcurrentHashMap——传统 FPM 进程隔离,**应用内不存在并发写问题**(一个请求一个进程);「并发问题」发生在共享外部资源(数据库/Redis),用事务/锁指令解决,与语言无关。
>
> ⚠️ Java 思维陷阱 3:想用 static 缓存跨请求——进程隔离,static 只活一个请求;跨请求共享必须 Redis/DB(这是 PHP 传统架构的固有约束)。

## 进阶:Swoole/Hyperf 协程(高并发 PHP)

- Swoole 扩展让 PHP 常驻内存 + 协程调度(≈ goroutine 的心智)。
- Hyperf 是基于 Swoole 的现代框架:**协程 + 依赖注入 + 注解路由**(≈ Java 微服务体验)。
- 此时才需要面对 Java 式问题:连接池、锁、内存泄漏(进程常驻)。

```php
// Swoole 协程示例(概念示意,需安装 swoole 扩展)
use Swoole\Coroutine;
use function Swoole\Coroutine\run;

run(function () {
    Coroutine::create(fn() => fetchData(1));  // ≈ goroutine
    Coroutine::create(fn() => fetchData(2));  // 并发执行
});
```

## 并发模式对照

| 场景 | Java | PHP(传统) | PHP(Swoole) |
|---|---|---|---|
| 并发请求外部 API | 线程池/异步 | **串行**(一个请求内顺序调) | 协程并发 |
| 后台任务 | 线程池/消息队列 | **消息队列**(必须外部化) | 协程/消息队列 |
| 定时任务 | @Scheduled | cron 脚本 | Hyperf 定时任务 |
| 长连接推送 | WebSocket 服务 | 需 Swoole/第三方 | Swoole 原生 |

## 性能认知

- 传统 PHP:**并发上限 = 进程数**(100 进程 ≈ 100 并发/秒级吞吐),高并发靠水平扩展(多机)或换架构。
- 但 PHP 单请求执行极快(脚本无常驻成本),静态内容站/CRUD 场景吞吐可观。
- Java:单实例可承载数千并发(线程池 + 异步),架构复杂度更高。
