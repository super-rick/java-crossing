# Go · 06 测试

> 锚点:Java 的 JUnit 5 + Mockito + JaCoCo 对应 Go 内置的 go test + 表驱动 + go test -cover。
>
> 验证环境:Go 1.26.7 / Windows 11(git-bash),示例均为实测输出。

**一句话:Go 把测试内建进语言:`go test` 即框架,`_test.go` 即测试类,表驱动是 Go 的 @ParameterizedTest。**

## 测试对照表

| 维度 | Java | Go |
|---|---|---|
| 框架 | JUnit 5(依赖引入) | go test(内置,零依赖) |
| 测试文件 | src/test/java/... 独立目录 | 与被测文件同目录,`xxx_test.go` |
| 测试方法 | @Test void method() | `func TestXxx(t *testing.T)`(首字母大写,Test 前缀) |
| 断言 | Assertions.assertEquals | `if got != want { t.Errorf(...) }`(无断言库,if 即断言) |
| 参数化 | @ParameterizedTest + @CsvSource | **表驱动**:结构体切片 + 循环 |
| 子测试 | @Nested | `t.Run(name, func(t *testing.T){...})` |
| 生命周期 | @BeforeEach/@AfterEach | 无内置;测试函数内自行处理,或用 TestMain |
| Mock | Mockito | 定义小接口 + 手写 stub;testify/mock 可生成 |
| 覆盖率 | JaCoCo(插件) | `go test -cover`(内置) |
| 基准测试 | JMH | `func BenchmarkXxx(b *testing.B)`(内置,Go 特色) |
| 断言失败 | 抛 AssertionError | t.Error(继续)/ t.Fatal(中止) |

## 完整对照示例(实测)

被测代码 `calc/calc.go`:

```go
package calc

import "fmt"

func Add(a, b int) int { return a + b }

func Divide(a, b int) (int, error) {
	if b == 0 {
		return 0, fmt.Errorf("divide by zero")
	}
	return a / b, nil
}
```

测试代码 `calc/calc_test.go`:

```go
package calc

import "testing"

func TestAdd(t *testing.T) {
	if got := Add(1, 2); got != 3 {
		t.Errorf("Add(1,2) = %d, want 3", got)
	}
}

// 表驱动测试(≈ @ParameterizedTest)
func TestDivide(t *testing.T) {
	cases := []struct {
		name string
		a, b int
		want int
		err  bool
	}{
		{"normal", 10, 2, 5, false},
		{"zero", 10, 0, 0, true},
	}
	for _, c := range cases {
		t.Run(c.name, func(t *testing.T) {
			got, err := Divide(c.a, c.b)
			if (err != nil) != c.err {
				t.Fatalf("err=%v, want err=%v", err, c.err)
			}
			if got != c.want {
				t.Errorf("got %d, want %d", got, c.want)
			}
		})
	}
}
```

运行:`go test ./calc -v -cover`
实测输出:

```

=== RUN   TestDivide

=== RUN   TestDivide/zero
```

## 关键差异

### 1. 断言 = if + t.Errorf
Go 没有断言库(标准派),风格是「条件不满足就报错」。第三方断言 testify 可选,但标准库派(if 风格)是主流。

### 2. 表驱动测试是 Go 的文化
Java 的 @ParameterizedTest 要学注解体系;Go 用「结构体切片 + range」,数据与断言代码分离,是 Go 社区默认写法——读别人测试时先找 `cases := []struct{...}`。

### 3. Mock:接口即 mock 点
- Java 的 Mockito 能 mock 具体类;Go 的惯例是**面向接口编程 + 手写 stub 实现**——mock 成本倒逼更小的接口设计(好事)。
- 需要自动 mock 时:testify/mock(生成)或 mockery(代码生成)。

### 4. 覆盖率门槛(CI 里用)

```bash
go test ./... -coverprofile=coverage.out
go tool cover -func=coverage.out | tail -1
```

> ⚠️ Java 思维陷阱 1:测试放独立目录 src/test——Go 测试与被测文件同目录同包(或 _test 外部包),没有双目录结构。
>
> ⚠️ Java 思维陷阱 2:过度 mock——Go 惯例「真实依赖 + 小接口」,能真连就真连(本地起依赖),mock 只在边界用。
>
> ⚠️ Java 思维陷阱 3:忘记测错误分支——Go 的 error 返回设计让「错误路径测试」是常态(见上例 TestDivide/zero),覆盖率低于 80% 会被 review 打回。

## CI 接入(Go 部分)

```yaml
- name: Go test
  run: go vet ./... && go test ./... -cover
```

本仓库 examples/go-order-service 的 CI 即此模式(见 .github/workflows/examples-test.yml)。
