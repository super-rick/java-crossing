# Go · 10 常见误区(Java 思维移植的坑)

> 锚点:把 Java 的习惯直接搬进 Go 会踩的坑。
>
> 验证环境:纯文档,坑位均来自前 09 个模块的实测示例与 Go 社区共识。

| # | 误区(Java 思维) | 后果 | 正确做法 |
|---|---|---|---|
| 1 | 用线程池管理并发 | 引入无意义的复杂度 | goroutine 即用即起,百万级不是问题 |
| 2 | 依赖 synchronized 自动解锁 | 忘记 defer 解锁 → 死锁 | `mu.Lock(); defer mu.Unlock()` |
| 3 | 所有并发都用锁 | 锁过多,可读性差 | 先想 channel 传值(CSP),锁留给临界区 |
| 4 | try/catch 处理业务错误 | Go 没有异常;panic 滥用会崩进程 | 错误返回值 + if err != nil |
| 5 | 找 implements 与继承体系 | Go 接口隐式实现,组合优先 | 小接口 + 结构体嵌入 |
| 6 | 变量声明了没用到没事 | **编译失败**(Go 零容忍) | 删除或用 `_` 忽略 |
| 7 | 认为 slice 赋值是拷贝 | 共享底层数组,意外改到原数据 | 需独立副本用 `append([]T{}, src...)` |
| 8 | append 不接返回值 | 扩容后原 slice 失效,静默丢数据 | `s = append(s, x)` |
| 9 | map 并发访问没事 | **直接 panic**(运行时检测) | sync.Mutex 或 sync.Map |
| 10 | map.get 不存在返回 null 判断 | Go 返回零值不报错 | 双返回值 `v, ok := m[k]` |
| 11 | 把 JVM 调优参数移植 | 找不到对应物;瞎调 GOGC 反增延迟 | GOMEMLIMIT 即可,其余信运行时 |
| 12 | 镜像里装 shell/工具 | 体积大、攻击面大 | scratch/distroless + 日志/pprof 排查 |
| 13 | 等框架送监控 | Go 无 Actuator,/metrics 和 /healthz 要自己写 | prometheus/client_golang + 手写 healthz |
| 14 | 测试放独立目录、找注解 | go test 同目录 `_test.go` | 表驱动 + t.Run 子测试 |
| 15 | 用 ThreadLocal 隐式传参 | Go 无线程局部变量 | context.Context 显式传递 |
| 16 | 找 Spring 全家桶 | Go 是组合文化,没有统一框架 | Gin + GORM + viper + slog 即事实标准 |
| 17 | 错误「懒得处理」 | err 被忽略 = 线上事故 | 每条 err 都要处理:返回、记录或显式忽略 |
| 18 | 认为标准库 http 是玩具 | 低估 net/http | 标准库就是生产级,需要路由/中间件再上 Gin |
| 19 | 值传递 vs 指针不敏感 | 大结构体拷贝浪费;想改值却用值接收者 | 明确值/指针接收者语义 |
| 20 | 部署后没日志没剖析 | 线上出问题只能重启 | pprof 对运行中进程采样 + 结构化 JSON 日志 |

## 总结

Go 的设计哲学是「显式优于隐式」:错误显式返回、锁显式管理、监控显式接入。Java 的「框架替你搞定」在 Go 里换成「你自己组合」——这不是缺失,是设计选择。**移植 Java 思维时,先问自己:Go 在这里的显式方式是什么?**
