# Go · 04 并发编程(Go 的灵魂)

> 锚点:Java 的 Thread/synchronized/线程池/CompletableFuture 对应 Go 的 goroutine/channel/Mutex/select。
>
> 验证环境:Go 1.26.7 / Windows 11(git-bash),示例均为实测输出。

**一句话:Go 的并发哲学是「不要通过共享内存来通信,而要通过通信来共享内存」(CSP 模型)。Java 的对抗式(线程+锁)vs Go 的协作式(goroutine+channel)。**

## 并发原语对照表

| 概念 | Java | Go |
|---|---|---|
| 并发执行单元 | Thread(OS 线程,1MB 栈) | **goroutine**(用户态,~2KB 起,动态增长) |
| 创建 | `new Thread(r).start()` / 线程池提交 | `go func(){ ... }()` |
| 等待完成 | `thread.join()` / Future.get() | `sync.WaitGroup` / `<-channel` |
| 互斥锁 | `synchronized` / `ReentrantLock` | `sync.Mutex` / `sync.RWMutex` |
| 并发安全容器 | ConcurrentHashMap | `sync.Map`(或 Mutex+map) |
| 线程池 | ThreadPoolExecutor | **不需要**(goroutine 即用即起) |
| 异步结果 | CompletableFuture / Future | channel(接收即同步等待) |
| 多路等待 | CompletableFuture.anyOf | `select { case ... }` |
| 定时任务 | ScheduledExecutorService | `time.After` / `time.Ticker` + select |
| 原子操作 | AtomicInteger | `sync/atomic`(1.19+ 泛型版) |
| 协程局部变量 | ThreadLocal | `context.Context`(显式传递) |

## 完整对照示例(实测)

### 1. goroutine + channel ≈ Thread + Future.get

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	// goroutine + channel 同步(≈ Thread + Future.get)
	var wg sync.WaitGroup
	ch := make(chan string)
	wg.Add(1)
	go func() {
		defer wg.Done()
		ch <- "hello from goroutine"
	}()
	msg := <-ch // 阻塞接收
	fmt.Println(msg)
	wg.Wait()
}
```

运行:`go run main.go`
输出:`hello from goroutine`

### 2. 生产者-消费者(有缓冲 channel)≈ 线程池 + 任务队列

```go
package main

import (
	"fmt"
	"sync"
	"time"
)

func worker(id int, jobs <-chan int, results chan<- int, wg *sync.WaitGroup) {
	defer wg.Done()
	for j := range jobs {
		time.Sleep(5 * time.Millisecond)
		results <- j * 2
	}
	_ = id
}

func main() {
	jobs := make(chan int, 3)
	results := make(chan int, 3)
	var wg2 sync.WaitGroup
	for i := 0; i < 2; i++ { // 2 个消费者(≈ 线程池 size=2)
		wg2.Add(1)
		go worker(i, jobs, results, &wg2)
	}
	for i := 1; i <= 3; i++ {
		jobs <- i
	}
	close(jobs) // 关闭后 range 消费完自动结束
	wg2.Wait()
	close(results)
	sum := 0
	for r := range results {
		sum += r
	}
	fmt.Println("sum:", sum)
}
```

运行:`go run main.go`
输出:`sum: 12`(1×2 + 2×2 + 3×2)

**对应关系**:`jobs` channel = 阻塞队列,2 个 goroutine = 线程池 2 个线程,`range jobs` = 队列消费循环,`close(jobs)` = 停止信号。

### 3. select ≈ CompletableFuture.anyOf(多路等待)

```go
c1 := make(chan string, 1)
c2 := make(chan string, 1)
c1 <- "fast"
select {
case m := <-c1:
	fmt.Println("c1:", m)
case m := <-c2:
	fmt.Println("c2:", m)
}
```

运行输出:`c1: fast`(哪个先就绪走哪个;都就绪随机选)

### 4. sync.Mutex ≈ synchronized

```go
package main

import (
	"fmt"
	"sync"
)

func main() {
	var mu sync.Mutex
	counter := 0
	var wg sync.WaitGroup
	for i := 0; i < 100; i++ {
		wg.Add(1)
		go func() {
			defer wg.Done()
			mu.Lock()
			counter++
			mu.Unlock()
		}()
	}
	wg.Wait()
	fmt.Println("counter:", counter)
}
```

运行:`go run main.go`
输出:`counter: 100`(无锁会是 ~70-90,必错)

> ⚠️ Java 思维陷阱 1:**把线程池思维带过来**——Go 里开 10 万 goroutine 完全正常(每个 ~2KB),不需要池化。Java 线程池的 core/max/队列参数在 Go 里不存在。
>
> ⚠️ Java 思维陷阱 2:**依赖 synchronized 的「自动释放」**——Go 的 `mu.Lock()` 不会自动解锁,必须 `defer mu.Unlock()`(忘了就死锁)。
>
> ⚠️ Java 思维陷阱 3:用共享变量 + 锁解决所有并发——Go 的惯例是先想「能不能用 channel 传值」,channel 让数据所有权随消息流动,少一半锁。
>
> ⚠️ Java 思维陷阱 4:ThreadLocal 的隐式传参——Go 用 `context.Context` 显式传递(超时/取消/元数据),没有隐式变量。

## 并发模式对照(生产场景)

| 场景 | Java 做法 | Go 做法 |
|---|---|---|
| 超时控制 | Future.get(timeout) | `select { case r := <-ch: ...; case <-time.After(3*time.Second): ... }` |
| 限流 | RateLimiter(Guava) | `golang.org/x/time/rate` |
| 取消传播 | 中断标志/CompletableFuture.cancel | `context.WithCancel` + `ctx.Done()` |
| 并发收集结果 | CompletableFuture.allOf | `errgroup.Group`(x/sync) |
| 单飞(合并请求) | 手写 | `singleflight.Group` |

## 性能对照(工程认知)

- goroutine 切换成本远低于线程:用户态调度(GMP),无内核态切换。
- Java 线程 = 1 个 OS 线程(1MB 栈);Go 100 万 goroutine ≈ 2GB 栈总量但按需增长,实际占用远小。
- 但:**goroutine 不是免费**——每个 goroutine 有调度开销,CPU 密集场景 Go 的并行度受 GOMAXPROCS 限制(默认=CPU 核数)。
- 结论:IO 密集场景 Go 优势巨大;CPU 密集场景与 Java 线程池相当(Go 略省内存)。
